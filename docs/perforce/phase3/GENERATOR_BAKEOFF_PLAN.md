# UE 超大工程 Wiki 生成器对照实验计划

**状态**：待排期  
**建议负责人安排时间**：下周  
**目的**：用真实 UE 项目任务验证候选生成方案，而不是依据 README、Star 或页面观感做架构决策。

## 1. 决策问题

实验需要回答：

1. 当前 OpenDeepWiki 生成器在代表性 UE Scope 上的主要质量瓶颈是什么？
2. CodeWiki 风格分层规划是否显著提升主题覆盖和跨模块理解？
3. 候选生成器是否适合做内嵌 .NET 实现、独立服务，还是只借鉴算法？
4. 增量更新时能否只更新必要页面，同时保持目录和引用稳定？
5. 哪种输出真正改善 AI CR、UE 编辑器 Agent 和新人理解，而不只是文档更长？

## 2. 参赛方案

最低配置：

- **A：Current OpenDeepWiki**：当前生成流程，作为真实基线。
- **B：Hierarchical Prototype**：基于统一 Inventory、Domain Planner、Scope Manifest 的最小原型；可以借鉴 CodeWiki。
- **C：CodeWiki**：在相同导出 Scope 上运行原生工具，作为外部生成内核基线。

可选：

- OpenWiki：观察 Agent-native、repo-local 文档形态。
- DeepWiki/Zread：仅在数据和许可允许时作为产品质量参考，不作为可复现实现基线。

所有方案使用相同源码快照、允许文件集、语言、模型等级和预算上限。无法对齐的条件必须记录，不能直接比较总分。

## 3. 样本选择

选择三个去标识但保留真实复杂度的 DocumentScope：

### S1：跨模块生命周期系统

- C++/接口/配置跨多个模块或插件。
- 存在初始化、释放、网络或对象生命周期不变量。
- 用于验证跨模块关系、关键约束和 AI CR 上下文。

### S2：大型 AI/Gameplay 子系统

- 文件数多、目录深、模块内包含多个能力域。
- 存在异步、Mass/Crowd/StateTree/行为类流程之一。
- 用于验证分层拆分、预算隔离和深层主题召回。

### S3：策划侧资产驱动工作流

- 同时涉及 C++ API、Blueprint/配置 Schema 和编辑器操作。
- 提供最小 UE Knowledge Package；不得把私有资产内容提交进测试仓库。
- 用于验证 Wiki + UE MCP 的任务帮助程度和版本握手。

每个样本记录：文件数、代码量、目录深度、模块数、语言、输入 token 估算和选取原因。

## 4. Ground Truth

在运行生成器前，由熟悉模块的工程师建立只用于评测的答案集：

- 10–20 个必须覆盖的主题。
- 5–10 条关键不变量/风险。
- 关键入口文件和跨模块边。
- 3–5 个常见修改或排障任务。
- 应明确标记为未知、禁止推断的资产/运行时事实。
- 推荐的最小测试或验证入口。

Ground truth 不作为生成器输入，防止答案泄漏。人类 steering 作为单独实验变量运行。

## 5. 固定实验条件

- 固定 P4 snapshot/manifest，禁止在实验中途 sync。
- 固定 DocumentScope/ContextScope 和文件大小限制。
- 固定模型版本、temperature、最大 token 和并发。
- 每个方案至少重复 2 次，用于观察稳定性；关键候选建议 3 次。
- 保存 planner 输入输出、工具读取记录、token、耗时、错误和最终文档。
- 对模型可见的项目名、用户名和路径做一致去标识化。
- 将冷启动全量与历史 CL 增量分开统计。

## 6. 评测维度

### 6.1 生成质量

| 指标 | 说明 | 建议权重 |
|---|---|---:|
| Topic Recall | Ground truth 关键主题被正确覆盖的比例 | 20% |
| Citation Correctness | 引用路径存在且确实支持结论 | 15% |
| Cross-module Accuracy | 关键依赖、流程和生命周期是否正确 | 15% |
| Hallucination Rate | 无依据事实、错误资产配置或过度确定结论 | 15% |
| Boundary Quality | 页面边界、重复专题和遗漏是否合理 | 10% |
| Incremental Precision | 历史 CL 中必要更新命中与无关重写情况 | 10% |
| Stability | 重跑后的 page ID、结构和核心结论稳定性 | 5% |
| Cost/Latency | token、时间、失败/重试成本 | 10% |

权重必须在查看结果前确认。除总分外，Hallucination 和 Citation 设置独立否决门槛。

### 6.2 消费任务

**AI CR**：选择 5–10 个历史 CL，在不提供作者最终修复说明的条件下，让同一 Review Agent 分别使用各方案上下文，评价：

- 真实问题召回、误报和严重度判断。
- 是否找到正确不变量、相关模块和验证入口。
- 引用是否能被复核。

**UE 编辑器 Agent**：在隔离测试工程/打包编辑器中执行 3–5 个可恢复任务，评价：

- 任务完成率、错误操作数、澄清次数。
- 是否正确识别版本不兼容和必须实时查询的状态。
- 文档缺失时是否安全停止而不是猜测。

**新人导览**：邀请不了解该模块的工程师完成限时问答或定位任务，记录正确率、完成时间和主观可读性。主观评分不能替代事实正确性。

## 7. 增量测试集

为每个样本选择若干历史 CL，至少覆盖：

- 普通实现修改。
- 新增/删除文件。
- move/rename。
- 模块或插件清单变化。
- Context-only 依赖变化。
- UE Metadata Schema 或 tool contract 变化。

记录每次变化的理论影响页面集合，与生成器实际修改集合比较：

```text
Precision = 必要且实际更新 / 所有实际更新
Recall    = 必要且实际更新 / 所有必要更新
```

目录/path 大面积无意义变化、未更新已失效结论、重复重写未受影响页面都应单独计数。

## 8. 执行角色与产物

建议安排：

- 1 名实验负责人：冻结条件、运行和收集产物。
- 每个样本 1 名领域评审人：提供 ground truth 并盲评。
- 1 名平台评审人：检查集成、部署、许可证和长期维护成本。

实验产物：

- `experiment-manifest.json`：快照、Scope、模型、预算和方案版本。
- 每次运行的完整中间产物、日志和成本摘要。
- 统一评分表、逐项证据和分歧记录。
- AI CR/UE task 结果及失败分类。
- 一页决策记录：选择、拒绝原因、风险和下一步 spike。

实验产物如含私有代码或项目信息，不进入公开仓库；这里只保留模板和去标识结论。

## 9. 决策门槛

建议在实验启动会议上确认数值，默认可采用：

- 新方案 Topic Recall 和 Cross-module Accuracy 有明确提升。
- Citation Correctness 不低于 95%，严重幻觉为 0。
- 三个样本均不存在因目录深度造成的静默漏扫。
- 增量 Recall 不低于 95%，且无关页面重写可接受。
- AI CR 或 UE 编辑器任务至少一类产生可复现提升，另一类不退化。
- 成本和耗时在可运营范围内，领域失败可隔离/重试。

可能结论不只“选 A 或 B”：

1. 保留当前引擎，只引入确定性 Inventory 和覆盖审计。
2. 在 .NET 中实现 CodeWiki 风格分层规划。
3. CodeWiki 作为独立可插拔生成服务。
4. 分场景路由：小 Scope 用 Legacy，大 Scope 用 Hierarchical。
5. 结果不足，先改善 UE Metadata/steering 后重测。
